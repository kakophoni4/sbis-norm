# Статусы отчётов и КВ/ИВ для 1С

## Назначение

1С передаёт идентификаторы только тех отчётов, которые она ранее отправила
через `POST /api/sbis/send-report-1c/`. Сервис не делает фоновый перебор
всех компаний: элементы пачки группируются по ИНН, для каждой организации
открывается одна сессия СБИС, а затем читаются её документы.

Адрес:

`POST /api/sbis/report-statuses-1c/`

## Первый шаг — статусы без файлов

```json
{
  "items": [
    {
      "external_id": "1c-uuid-001",
      "inn": "7733419099",
      "sbis_doc_id": "идентификатор из send_meta.sbis_doc_id"
    }
  ],
  "include_files": false
}
```

Не более 50 документов на один запрос. `external_id` не обязателен, но
возвращается без изменений и нужен 1С, чтобы сопоставить ответ со своим
документом.

Основные статусы:

| `status` | Значение |
| --- | --- |
| `created` | создан / черновик |
| `preparing`, `signing`, `processing` | промежуточная обработка |
| `sent` | отправлен, ожидается доставка |
| `delivered` | доставлен, ожидается результат ФНС |
| `accepted` | принят |
| `rejected` | отказ или не принят |
| `unknown` | новый/неизвестный код СБИС — использовать `code`, `title`, `raw_state` |

Ответ всегда сохраняет сырой код СБИС (`code`) и исходное состояние
(`raw_state`), поэтому новый статус не теряется из-за нашей нормализации.

## Второй шаг — КВ и ИВ только для принятых

Когда 1С увидела `accepted`, она повторяет запрос для таких документов:

```json
{
  "items": [
    {
      "external_id": "1c-uuid-001",
      "inn": "7733419099",
      "sbis_doc_id": "идентификатор из send_meta.sbis_doc_id"
    }
  ],
  "include_files": true,
  "include_content": true
}
```

Для принятого отчёта в `files.kv` и `files.iv` возвращаются PDF в
`content_b64`, имя, размер и SHA-256. PDF сохраняются на сервере в
`media/one_c_receipts/<inn>/<sbis_doc_id>/`; при следующем запросе они
берутся из этого кэша без повторного скачивания из СБИС.

Возможные состояния отдельного файла: `ready`, `missing`, `forming`,
`no_pdf_url`, `http_<код>`, `transport_error`, `archive_error`. Для
`forming` 1С должна повторить второй шаг позже. Если у вложения нет прямой
ссылки, сервис один раз пробует архив документа; это не запускает новый
поиск прокси.

Если 1С хочет только узнать, появились ли файлы, без большого тела ответа,
передаётся `include_files: true, include_content: false`. При `ready`
будут метаданные и SHA-256 без `content_b64`.

## Ответ

```json
{
  "success": true,
  "items": [
    {
      "external_id": "1c-uuid-001",
      "inn": "7733419099",
      "sbis_doc_id": "...",
      "success": true,
      "code": "7",
      "status": "accepted",
      "title": "Принят",
      "description": null,
      "raw_state": {"Код": 7, "Название": "Принят"},
      "files": {
        "kv": {"state": "ready", "filename": "kv.pdf", "size": 12345, "sha256": "...", "content_b64": "..."},
        "iv": {"state": "forming"}
      }
    }
  ],
  "summary": {"total": 1, "ok": 1, "errors": 0, "include_files": true, "include_content": true}
}
```

Ошибки одной организации или одного отчёта не прерывают остальную пачку:
они возвращаются в элементе как `error.type` (`auth_error`, `sbis_error`,
`transport_error`, `validation_error`). HTTP 400 выдаётся только при
некорректной пачке целиком.

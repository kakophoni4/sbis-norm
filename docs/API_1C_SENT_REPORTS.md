# Отправленные отчёты и исходные XML для 1С

Реализовано в коде 01.10.2026. Перед использованием требуется развертывание
и проверка на сервере. Методы только читают СБИС, ничего не отправляют и не подписывают.
Текущий охват — отчёты ФНС (`ОтчетФНС`), включая отправленные не через наш сервис.
ПФР/СФР, Росстат, требования и обычный ЭДО в эту выдачу не входят.

## Общие правила

- Базовый адрес: `https://api.crmkanasha.org`.
- HTTPS, метод POST, `Content-Type: application/json`.
- Обязательный заголовок `X-1C-API-Token: <существующий токен>`.
- ИНН передавать строкой из 10/12 цифр.
- Даты `YYYY-MM-DD`; время `YYYY-MM-DDTHH:MM:SS` в московском времени,
  без преобразования даты документа в дату отправки.
- Пустые/неизвестные реквизиты возвращаются как `null`, неизвестный код статуса
  не заменяется предположением.
- Нельзя считать HTTP 200 самостоятельным подтверждением полноты: проверять
  `success`, а в методе списка также `complete` и `errors`.
- Не записывать токен и Base64 в общедоступные логи.

## 1. POST /api/sbis/sent-reports-1c/

Запрос:

```json
{"inn":"9729355495","days":30}
```

`days`: JSON-число, целое от 1 до 3660. Последние N календарных дней,
включая сегодня, по фактической отправке (московское время).
В ответ включаются и отправленные, но не принятые отчёты.

Пример ответа (даты условные):

```json
{
  "success":true,
  "complete":true,
  "inn":"9729355495",
  "date_from":"2026-09-02",
  "date_to":"2026-10-01",
  "timezone":"Europe/Moscow",
  "document_type":"ОтчетФНС",
  "count":1,
  "pages_read":1,
  "errors":[],
  "items":[{
    "sbis_doc_id":"eea440ed-6d5d-4ec4-9565-ca7d9bf91045",
    "document_date":"2026-09-16",
    "report_year":"2025",
    "period_code":"21",
    "sent_at":"2026-09-16T15:39:47",
    "sent_date":"2026-09-16",
    "correction_number":"0",
    "status_code":"9",
    "status":"Отчет не сдан",
    "status_description":""
  }]
}
```

`sbis_doc_id` — именно `Документ.Идентификатор`, не идентификатор внутреннего
комплекта или документооборота. Для скачивания передавать его и `sent_date`.
`report_year`, `period_code`, `correction_number` берутся из `Расширение`.
Статус/описание передаются из `Состояние` без перевода по собственной таблице.

Внутренние комплекты, удалённые документы и неотправленные черновики исключаются.
Код периода не следует универсально переводить в квартал без учёта формы отчёта.

### Полнота и экономия запросов

СБИС фильтрует список по **дате документа**, поэтому сервис намеренно не задаёт
`ДатаС/ДатаПо`: иначе потеряется старый документ, отправленный недавно.
Читает страницы по 100 документов, проверяет ИНН каждого документа.
Для определения отправки читает событие `ДекларацияНП` либо событие со статусом `3`.
Дату создания или получения подтверждения вместо отправки не использует.
Если в карточке несколько таких событий, используется наиболее раннее.

Одна авторизация на запрос. Установленные даты отправки кешируются по ИНН,
документу, редакции и номеру отправки; статусы перечитываются из списка.
Первое сканирование большой организации может потребовать нескольких запросов.
Рабочий бюджет сканирования — около 100 секунд (текущий сетевой вызов может
завершиться позже), максимум 100 страниц. При лимите или ошибке:

```json
{"success":false,"complete":false,"items":[],"errors":[{"code":"scan_limit","message":"Лимит времени; повторите запрос для продолжения проверки"}]}
```

Реальный неполный ответ содержит также остальные поля обычного ответа.
`items` может содержать уже найденные записи. Их можно сохранить по ключу
`inn + sbis_doc_id`, но нельзя удалять отсутствующие записи или считать сверку полной.
Повторять тот же запрос с паузой; кеш дат сокращает повторную работу.
`send_date_unknown` означает, что документ не включён: дату отправки установить
не удалось. Повторный запрос не гарантирует исправления этого случая.
`pagination_error` — неполная/повторяющаяся навигация СБИС; не считать список полным.

## 2. POST /api/sbis/sent-report-xml-1c/

```json
{
  "inn":"9729355495",
  "sbis_doc_id":"eea440ed-6d5d-4ec4-9565-ca7d9bf91045",
  "sent_date":"2026-09-16"
}
```

Ответ:

```json
{
  "success":true,
  "inn":"9729355495",
  "sbis_doc_id":"eea440ed-6d5d-4ec4-9565-ca7d9bf91045",
  "sent_date":"2026-09-16",
  "sent_at":"2026-09-16T15:39:47",
  "cached":false,
  "files":[{
    "name":"NO_NDS_....xml",
    "role":"report",
    "size":1234,
    "sha256":"...",
    "content_base64":"..."
  }]
}
```

`files` содержит исходные неслужебные исходящие XML. Для НДС роли:
`report` — декларация, `purchase_book` — `NO_NDS.8_*`,
`sales_book` — `NO_NDS.9_*`. Если книги отсутствуют, их нет в массиве.
Квитанции, извещения, уведомления об отказе и подписи не возвращаются.
При наличии вложений в событии отправки используются они, а не более поздняя редакция.

В 1С декодировать Base64 в двоичные данные и сохранить с указанным именем.
Не перекодировать: возвращаются исходные байты, в том числе Windows-1251.
Перед скачиванием проверяются принадлежность документа ИНН и дата отправки.
Лимиты: 20 XML, суммарно 64 МиБ до Base64. Зашифрованные/упакованные вложения
пока возвращают `unsupported_attachment`, а не неполный успешный комплект.

Полностью скачанный комплект атомарно сохраняется в закрытом каталоге
`private_cache/sent_reports/` в корне проекта, **не в публичном media**.
Повторный запрос возвращает `cached:true` без авторизации и обращений к СБИС.
Перед выдачей кеша проверяются размер и SHA-256. Кеш — сохранённый снимок
комплекта, автоматического обновления после изменения документа в СБИС нет.
Не настраивать nginx на публичную раздачу этого каталога; включить его в защищённые резервные копии.

## Ошибки

Формат: `{"success":false,"error":{"code":"...","message":"..."}}`.

| HTTP | Случай |
|---|---|
| 400 | Некорректный ИНН, days, UUID, дата или JSON не объект |
| 401/403 | Нет/неверен токен (зависит от настроек DRF) |
| 404 | Документ другого ИНН / не найден основной XML |
| 409 | Неотправленный документ, неизвестная или несовпадающая дата отправки |
| 413 | Превышен лимит файла/комплекта |
| 502 | Ошибка авторизации/СБИС/скачивания, нет ссылки, неподдерживаемое вложение |
| 500 | Внутренняя ошибка сервиса |

При проблеме одного файла полный комплект не кешируется и успешный ответ не выдаётся.
Разрешены только HTTPS-ссылки СБИС/Saby; перенаправления не выполняются.

## Порядок работы в 1С

1. Выполнить POST `https://api.crmkanasha.org/api/sbis/sent-reports-1c/` с ИНН и days.
2. Проверить HTTP-код, `success` и `complete`. При неполном ответе сохранить найденные
   записи, но не считать сверку завершённой. Повторы делать с паузой, не параллельно.
3. Для нужного отчёта взять `sbis_doc_id` и `sent_date` из ответа.
4. Выполнить POST `https://api.crmkanasha.org/api/sbis/sent-report-xml-1c/` с тем же ИНН.
5. При `success:true` декодировать каждый `content_base64` и сохранить файл.
   Для недостающих книг не создавать пустые файлы. SHA-256 относится к байтам после Base64.
6. Повторные XML-запросы допустимы: готовый комплект возвращается из кеша.

На стороне HTTP-клиента установить таймаут не меньше 180 секунд.
Для одного ИНН не запускать несколько сканирований одновременно.
Первый метод возвращает метаданные, второй — файлы; эти методы ничего не
отправляют в налоговую и не меняют статус отчёта.

Инструкция для администратора отдельно: [DEPLOY_1C_SENT_REPORTS.md](DEPLOY_1C_SENT_REPORTS.md).

Основание пагинации: https://saby.ru/help/integration/api/all_methods/list_doc
Поля отчётного периода/событий проверены на ответах ЗЕРО от 01.10.2026.
